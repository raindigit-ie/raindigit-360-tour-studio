# RainDigit 360 Tour Studio — Product Readiness Contract

## Starter
- Purpose: define the product, UX, data-safety, performance and release requirements that must remain true.
- Audience: engineers, reviewers and operations owners.
- Read full when: changing the wizard, persistence, builders, packaging or employee workflow.
- Last update: 2026-08-16

## Product boundary

The Studio is a local-first production application. It turns already stitched panoramas into an editable tour and deterministic static releases. It does not own camera ingestion, customer CRM, public CMS content or production credentials. Operators prepare and approve a package; a publisher promotes it.

## Canonical UI kit

- `web-tour/css/tour.css` defines shared Studio tokens: control heights, radii, surfaces, focus ring and motion.
- Every step reuses `.editor-button`, `.editor-field`, `.editor-step-heading`, `.editor-publish-card`, `.editor-disclosure`, status and card primitives. A feature must not introduce a one-off button, field or focus treatment.
- One stage has one user goal and at most one primary action. Advanced or technical actions start collapsed.
- Mobile Studio controls are at least 36px in the automated contract; normal and primary controls use 40/44px tokens. Published-tour toolbar controls are at least 40px and route controls at least 36px.
- Focus is visible, controls have accessible names, fields have labels, IDs are unique, reduced-motion is respected, the sticky footer stays inside the viewport and the document has no horizontal overflow.

## Data safety

- Project and draft writes are atomic and revision-checked.
- Offline/transient failure retries use bounded exponential backoff; stale writes never retry over newer data.
- Downloads do not mutate the workspace.
- Build validation reports incomplete data and never prunes scenes or media.
- Archive is explicit, versioned, integrity-tested and completed before clearing the workspace.
- Imports are transactional per file: a failed file rolls back its derived files and does not cancel valid siblings.

## Build and performance model

- The primary action builds only the optimized versioned web package. This is the ordinary RainDigit/R2 path.
- Portable HTML, paste-in code and legacy folder ZIP are generated by a separate optional action, preventing duplicate panorama processing during normal work.
- Build progress exposes phase and percentage. Completion includes measured duration for evidence.
- The generated tour keeps a first-frame image visible until WebGL and runtime styles are ready. It must not show a black or unstyled intermediate frame.
- Release assets contain no editor endpoints, draft data or camera metadata.
- The employee launcher reuses a healthy local runtime. It rebuilds only on first use or when an engineer explicitly sets `RAINDIGIT_REBUILD=1`.

## Automated gates

`npm run test:all` must pass before commit. It covers:

- static/type/build checks;
- server contracts, stale-write rejection, archive integrity and non-destructive build failure;
- the complete employee wizard at mobile and desktop sizes;
- touch target, accessible-name, field-label, duplicate-ID, overflow and primary-action contracts;
- walking-button persistence and Polish/final-view geometry;
- optimized and optional portable builds;
- offline single-file opening, iframe embedding, distribution kit and release-browser checks;
- first-paint/performance behavior of the multires tour.

`npm run test:all:verified` is the evidence-producing wrapper. It uses the testing-lab core profile because this local-first product has no quality/observability service integration to exercise. Keep its output with the run note used for a release decision.

`npm run setup:hooks` installs the versioned local pre-push gate. The full suite runs locally before a push, so the private project does not depend on paid CI minutes for its primary quality decision.

## Change policy

1. Reproduce a reported issue in an isolated workspace; never mutate the employee's active `studio-workspace` during diagnosis.
2. Add or strengthen a regression assertion before considering the fix complete.
3. Verify the full wizard, not only the changed screen.
4. Update this contract, the operator playbook and Kimi Base when product behavior changes.
5. Commit with both repositories clean. Generated workspaces, media, releases and credentials never enter Git.
